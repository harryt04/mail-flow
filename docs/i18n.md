# i18n — internationalization scaffolding

## Purpose
Centralizes every UI-facing string (headings, buttons, placeholders, aria-labels, TTS/voice
prompts, and API error messages surfaced to users) into one message catalog instead of hardcoded
English scattered across components. Built with [`next-intl`](https://next-intl.dev). Only
`en-US` exists today — the point of this scaffolding is that adding a second language later is
"add a JSON file," not a re-architecture.

There is **no URL-based locale routing** (no `/en-US/...` prefixes). Locale is resolved
server-side per request and stuck in a cookie — see "Locale resolution" below.

## Key files
| File | Role |
|---|---|
| `src/messages/en-US.json` | The message catalog — single source of truth for every UI string. Namespaced by feature area, mirroring `src/app/` and `src/components/` (e.g. `settings`, `listen`, `landing`, `nav`, `common`). |
| `src/i18n/config.ts` | `locales`, `defaultLocale`, `Locale` type, `localeCookieName`. The one place to add a new locale. |
| `src/i18n/request.ts` | `next-intl`'s `getRequestConfig` — reads the `NEXT_LOCALE` cookie, loads the matching `messages/<locale>.json`. |
| `src/i18n/messages.d.ts` | Declares `IntlMessages` from the `en-US.json` shape so `t('some.key')` calls are typo-checked by TypeScript. |
| `proxy.ts` | Already runs on every request for auth gating (see [proxy-and-routing.md](./proxy-and-routing.md)) — also negotiates `Accept-Language` against `SUPPORTED_LOCALES` and sets the `NEXT_LOCALE` cookie on first visit if not already set. |
| `src/app/layout.tsx` | Wraps the app in `NextIntlClientProvider`, fetched via `getLocale()`/`getMessages()`. |
| `src/lib/errors/apiErrorCodes.ts`, `src/lib/errors/translateApiError.ts` | API error-code catalog and the client-side helper that translates a route's `code` field — see "API errors" below. |
| `src/test/renderWithIntl.tsx` | Test-only render helper wrapping a component in `NextIntlClientProvider` with the `en-US` catalog — use for any component test whose component calls `useTranslations`. |

## Conventions
- **No bare string literals in JSX.** Add a key to `messages/en-US.json` under the relevant
  namespace, then read it with `useTranslations('namespace')` (client components) or
  `getTranslations('namespace')` (server components — `page.tsx`, `layout.tsx`, and any
  non-`'use client'` component). This is enforced by an ESLint rule
  (`i18next/no-literal-string`, scoped to `src/app/**/*.tsx` and `src/components/**/*.tsx` in
  `eslint.config.mjs`) — expect it to need occasional tuning (new `ignoreAttribute` entries) as
  the codebase grows, and use a targeted `eslint-disable-next-line` with a comment for genuine
  non-prose exceptions (e.g. the `"1.5x"` playback-speed suffix in `ListenClient.tsx`).
- **Rich text / embedded links** use `t.rich('key', { tag: (chunks) => <a>{chunks}</a> })` with
  `<tag>...</tag>` markup inside the message string (see `landing.signIn.consent` for an
  example), not string concatenation.
- **Pluralization / numbers** use ICU MessageFormat directly in the message string (e.g.
  `"{total, plural, one {# email} other {# emails}}"`, `"{count, number}"`) rather than manual
  JS pluralization logic.
- **Dates/relative time** use `next-intl`'s `useFormatter()` (see `InboxClient.tsx`'s
  `formatRelativeTime`) instead of hardcoding a locale in `toLocaleDateString`.

## API errors
API routes (`src/app/api/**/route.ts`) return a stable machine-readable `code` field alongside
the existing English `error` string (kept as a dev/log-friendly fallback, not shown to users).
Codes are typed in `src/lib/errors/apiErrorCodes.ts` and translated via the `apiErrors` namespace
in the message catalog. Client call sites use `translateApiError(tApiErrors, payload, fallback)`
instead of displaying `payload.error` directly — see `ListenClient.tsx`'s `postJson`,
`InboxClient.tsx`'s jump handler, or `SettingsClient.tsx` for examples. New routes should follow
the same pattern: `{ error: 'English message', code: 'SOME_CODE' }`, with `SOME_CODE` added to
both `apiErrorCodes.ts` and the `apiErrors` namespace.

## Locale resolution
No URL routing — the resolved locale lives in a `NEXT_LOCALE` cookie, set once by `proxy.ts` on
a visitor's first request (negotiated from the `Accept-Language` header against
`src/i18n/config.ts`'s `locales`, falling back to `defaultLocale`). `src/i18n/request.ts` reads
that cookie on every subsequent request. This means every route (including the unauthenticated
landing page, `/privacy`, `/tos`) gets a resolved locale, not just the `(authenticated)` group.

## Voice command phrases
`src/lib/voice/commandMatcher.ts`'s spoken-command vocabulary (`COMMAND_PHRASES`,
`MOVE_TRIGGERS`) lives in the `voice` namespace of the message catalog too — centralized
alongside everything else, but **still English-only**. True multi-language voice support needs
the STT provider's language to switch in lockstep with the phrase list (see
[lib/voice.md](./lib/voice.md)), which is out of scope for this scaffolding.

## Where to add new code here
- **A new UI string** → add a key under the relevant namespace in `messages/en-US.json`, read it
  with `useTranslations`/`getTranslations` at the call site. Don't invent a new top-level
  namespace for a single string — nest under the existing feature namespace.
- **A new page/feature area** → add a new top-level namespace to `messages/en-US.json` named
  after the route/component (matches the existing `settings`, `listen`, `landing`, etc. pattern).
- **A new locale** → add it to `src/i18n/config.ts`'s `locales` array, add
  `src/messages/<locale>.json` with the same key shape as `en-US.json`. No routing or component
  changes needed — `next-intl` and the `Accept-Language` negotiation in `proxy.ts` pick it up
  automatically.
- **A new API error case** → add the code to `src/lib/errors/apiErrorCodes.ts`'s `ApiErrorCode`
  union and to the `apiErrors` namespace, return `{ error, code }` from the route.
